# AI Document Checker Service

Backend-сервис автоматизированной проверки документов.

Приложение принимает пакет PDF-документов, определяет их тип, проверяет полноту комплекта, сохраняет результаты проверки в базе данных и предоставляет REST API для получения информации о выполненных проверках.

---

# Используемые технологии

| Технология | Назначение |
|------------|------------|
| Python 3.11 | Основной язык разработки |
| FastAPI | Создание REST API |
| SQLAlchemy 2.0 (Async) | Асинхронная работа с базой данных |
| PostgreSQL | Хранение данных |
| Alembic | Управление миграциями базы данных |
| Pydantic v2 | Валидация данных |
| Docker + Docker Compose | Контейнеризация приложения |
| Uvicorn | ASGI-сервер |
| Pytest | Тестирование |

## Почему выбран именно этот стек

- **FastAPI** позволяет быстро создавать производительные REST API и автоматически генерирует OpenAPI-документацию.
- **SQLAlchemy Async** обеспечивает удобную асинхронную работу с PostgreSQL.
- **PostgreSQL** является надежной промышленной реляционной СУБД.
- **Alembic** позволяет безопасно управлять изменениями структуры базы данных.
- **Docker** обеспечивает одинаковое окружение для разработки и запуска проекта.
- **Pytest** используется для написания и запуска автоматических тестов.

# Архитектура проекта

Проект реализован с использованием многослойной архитектуры.

```
app/
├── api/
│   └── v1/
│       └── endpoints/      # REST API
│
├── core/                   # Конфигурация приложения и БД
│
├── dao/                    # Работа с базой данных
│
├── models/                 # SQLAlchemy модели
│
├── schemas/                # Pydantic схемы
│
├── services/               # Бизнес-логика
│
├── storage/                # Работа с файловым хранилищем
```

### Слои приложения

- **API** — обработка HTTP-запросов.
- **Services** — основная бизнес-логика проверки документов.
- **DAO** — взаимодействие с PostgreSQL.
- **Models** — описание структуры таблиц.
- **Schemas** — модели запросов и ответов.
- **Storage** — сохранение загруженных файлов.

Такое разделение позволяет изолировать бизнес-логику от работы с HTTP и базой данных, упрощает сопровождение и тестирование приложения.

# Запуск проекта

## Требования

- Docker
- Docker Compose

## 1. Клонировать репозиторий

```bash
git clone <repository_url>
cd document-checker-service
```

## 2. Создать файл окружения

```bash
cp .env.example .env
```

или вручную создать `.env` на основе `.env.example`.

## 3. Запустить приложение

```bash
docker compose up --build
```

## 4. Применить миграции

```bash
docker compose exec app alembic upgrade head
```

После запуска приложение будет доступно по адресу

```
http://localhost:8000
```

Swagger:

```
http://localhost:8000/docs
```

# Основные REST API

## Создание проверки

```
POST /api/v1/checks
```

Форма (`multipart/form-data`):

- **files** — список PDF-документов;
- **program** — `federal` или `regional`.

Возвращает результат проверки документов.

---

## Получение списка проверок

```
GET /api/v1/checks
```

Возвращает список всех выполненных проверок.

---

## Получение информации о проверке

```
GET /api/v1/checks/{check_id}
```

Возвращает подробную информацию о конкретной проверке.

---

# Структура хранения данных

При выполнении проверки создаются:

- запись о проверке (`Check`);
- записи о загруженных документах (`Document`);
- версии документов (`DocumentVersion`).

Все сущности связаны между собой через UUID-идентификаторы.
